# Waypoint v1 spec

Charted on the map [Waypoint: chart the way to a v1 spec](https://app.clickup.com/t/1241uyj530k). Every decision below is detailed in a closed ticket on that map; this spec gathers them for an implementer. Terms follow `GLOSSARY.md`.

## Problem Statement

People carry life-level wants ("get fit again", "learn Spanish", "start my own company") that never turn into steady progress. Generic to-do and habit apps leave the hard parts to them: working out a realistic route from where they stand, fitting it into the time they actually have, and picking themselves up after a missed week without guilt. Plans made in a burst of motivation are too ambitious, nothing adapts when life gets in the way, and a broken streak becomes the reason to quit. Progress is invisible or measured by outcomes the person can't control week to week, so they can't tell whether they're on course or whether what they're doing is working.

## Solution

Waypoint is an Android app with an LLM Coach. The user names an Aspiration; the Coach runs a warm, one-question-at-a-time Interview, then proposes a Plan: dated Milestones reached by effort or ability, habits placed on the user's free Slots or tied to Anchors in their routine, and concrete Actions laid out two weeks ahead, starting gently and ramping up. Each Action gets one well-timed reminder with Done · Partly · Skip right in the notification shade. Every week the Coach proposes the next week and, when Check-ins show a pattern, a kind Re-plan the user approves. Progress is shown honestly: Pace (time given versus planned), a Projection in words of when each Milestone's work will be done, and an optional Measure that tests whether the Plan is working. When life intervenes, a Pause sets Actions aside without blame. The Coach is forgiving, never strict, and when it can't reach its model it is late, never faked.

v1 is built for one user (the developer), on foundations (Google sign-in, a `UserId` on every row, a server-side model key) that could take other users later.

## User Stories

### First run and Interview

1. As a new user, I want three short swipe cards explaining what Waypoint does, so that I know what I'm signing up for before I sign in.
2. As a new user, I want to sign in with Google, so that I don't create another password.
3. As a new user, I want a "Step n of 4" counter (Sign in → Aspiration → Interview → First Plan), so that I know how long setup takes.
4. As a new user, I want example chips under "What do you want to reach?", so that I can start from a suggestion when I'm not sure how to phrase it.
5. As a user, I want the Interview to be a chat with one question per turn, so that it feels like talking to a coach rather than filling a form.
6. As a user, I want the Coach to reflect back what I said before asking the next question, so that I feel heard.
7. As a user, I want the Coach to ask what success looks like, why now, my starting point, my past attempts and what derailed them, my time, my constraints, my dates and how I want to be coached, so that the Plan fits me.
8. As a user, I want the Coach to pin each Slot to a day and time window and ask whether travel eats into it, so that Actions are placed in time I really have.
9. As a user with a physical Aspiration, I want the Coach to ask once about health and injuries, so that the Plan doesn't hurt me.
10. As a user, I want a short domain block (current routine, skill level, limits like allergies or equipment, strong likes and dislikes), so that Guides fit me.
11. As a user, I want to state what I'd settle for as a later date, a smaller picture, or both, so that I'm not forced to think in deadlines.
12. As a user, I want to choose how the Coach reacts when I skip (gentle check, quiet re-plan, or ask why), so that skips are handled the way I like.
13. As a first-time user, I want to set my Slots, total Time budget and Contact frequency once, in my first Interview, so that later Interviews are shorter.
14. As a user, I want a "What I've heard" strip on top of the Interview that lights up as answers come in and unfolds on tap, so that I can see the picture forming.
15. As a user, I want answer chips under the input where they help, so that I can answer common questions in one tap.
16. As a user, I want to "Save and leave" an Interview and resume it later, so that I don't have to finish in one sitting.
17. As a user reopening an interrupted first run, I want to land straight back in the step I left, with the Coach recapping and repeating its last question, so that I pick up without friction.
18. As a user, I want the Coach to propose a short name for the Aspiration (editable, at most 16 characters), so that it reads well on chips and filters.
19. As a user, I want the Interview to end with a short second-person picture, the things the Coach still doesn't know, and my dates, time a week and Slots, so that I can check it got me right.
20. As a user, I want "That's right" or "Correct something" on the picture, so that I can fix a misunderstanding before the Plan is drafted.
21. As a user, I want the Interview to take about 10–12 Coach turns, so that it's thorough without dragging.
22. As a user, I want a summary card of the Interview to land in the Coach chat, so that I can find it later and correct it.
23. As a user, I want a "Drafting your Plan" wait that tells me the Plan will wait on Today if I leave, so that I'm not stuck staring at a spinner.

### Plan and Plan review

24. As a user, I want the Coach to propose a Plan with a short rationale tied to my starting point, past derailers and time, so that I understand why the route fits me.
25. As a user, I want about 3–6 Milestones, the first within 2–4 weeks, so that I get an early win.
26. As a user, I want every Milestone to carry a "reached when" line about work done or an ability gained, so that doing the planned work can never end in a "failed" Milestone.

28. As a user, I want the Coach to name the assumptions it made, so that I can correct them.
29. As a user, I want concrete Actions only two weeks ahead, so that the Plan stays realistic and easy to change.

31. As a user, I want no day to hold more Actions than its Slots, so that the Plan is doable.
32. As a user with several Aspirations, I want each to get at least one Action a week and the one closest to slipping past its Settle-for line to win a contested Slot, so that I never have to rank them by hand.

38. As a user, I want nothing scheduled until I approve, so that the Plan stays mine.
39. As a user, I want every approved change kept as a Plan version with its reason, so that history and Projections stay honest.
40. As a user, I want to move a single Action myself, so that small changes don't need the Coach.
41. As a user, I want behaviour habits (eat at home, walk after dinner) tied to an Anchor in my routine instead of a Slot, so that they don't eat my Time budget.

46. As a user, I want Today to show a timeline of my Actions with a time column and a "now" line, so that I see my whole day and where I am in it.

59. As a user, I want "Not today" to offer just this Action, everything for the rest of today, or a few days, so that I can step back without blame.

### Reminders and notifications

60. As a user, I want one reminder per Action, at the Slot's start for "now" Actions or a lead time ahead for "get-ready" Actions, so that it reaches me when it helps.
61. As a user, I want to change an Action's lead time, so that reminders fit my routine.
62. As a user, I want Actions that fire at the same moment grouped into one notification, so that I'm not spammed.
63. As a user, I want Done · Partly · Skip on each reminder in the shade and on the lock screen, even when the app was killed, so that I can check in without opening the app.
64. As a user, I want Partly in the shade to ask "what did you get done?" inline, so that I can give minutes without opening the app.
65. As a user, I want reminders to fire even during quiet hours if I placed a Slot there, so that the Plan I accepted is honoured.
66. As a user, I want at most one warm follow-up at the end of a Slot, and none when it doesn't help, so that I'm not nagged.
67. As a user, I want an Action I didn't report to stay unreported, never assumed skipped, so that forgetting to tap isn't counted against me.
68. As a user, I want unprompted Coach messages capped by my Contact frequency (Quiet · Gentle · Chatty) across all Aspirations, so that the Coach reaches out as often as I like and no more.
69. As a user, I want quiet hours (21:30–07:00 by default, editable) during which Coach messages wait, so that I'm not disturbed at night.
70. As a user, I want a reminder tap to open Today with that Action's sheet, a Coach message to open the chat, and "Plan ready" to open Plan review, so that a tap lands where I need to be.
71. As a user, I want notification and exact-alarm permissions asked one at a time, right after my first Plan is approved, each with why it's needed and what happens without it, so that I understand what I'm granting.
72. As a user who declined exact alarms, I want reminders to still arrive, up to about an hour late, and a calm warning in Settings with "Allow exact alarms", so that I can change my mind.
73. As a user whose phone kills Waypoint in the background, I want to be told and deep-linked to the right battery setting, so that reminders start landing again.
74. As a user who's gone quiet, I want one gentle nudge after 3 days and a second after 7 that offers a Pause, then nothing more, so that silence never feels like failure.
75. As a user, I want the weekly refresh prompt as one notification at my chosen day and time, with "Looks good" accepting from the shade, so that weekly planning takes one tap.

### Weekly refresh, misses and Re-plan

76. As a user, I want the Coach to propose next week on a day I pick (what's planned, what changed and why), so that the Plan keeps moving.
77. As a user who ignores the weekly proposal, I want it to apply itself after a day with only a note in the app, so that the Plan never stalls.
78. As a user, I want the weekly refresh to first list the week's unreported Actions with a one-tap "did it", so that forgotten Check-ins are counted fairly.
79. As a user, I want one miss never to bend my Plan, so that a bad day stays a bad day.
80. As a user, I want the Plan to step down a notch when I've done under about 70% over two weeks, so that it meets me where I am.
81. As a user who's done under about 30% for two weeks, I want a short warm conversation about what changed instead of a quietly cut Plan, so that we fix the real problem.
82. As a user who missed a habit session, I want an offer to move it to a free Slot later that week, so that I can make it up if I want.
83. As a user who missed a task, I want it to move to the next free Slot with a one-line mention, and an offer to split it if it slips twice, so that Milestone work never just disappears.
84. As a user who keeps logging Partly on an Action, I want a shorter version offered after three in a row, so that the Action fits.
85. As a user who is keeping up, I want lost time folded into the next weeks (Catch-up, at most ~3 weeks and ~20% over my share), always proposed, with "just shift the dates" as an option, so that Milestones can keep their dates.
86. As a user who is struggling, I want shortfalls to move dates instead of piling on Catch-up, so that I'm not buried.
87. As a user, I want Milestone dates moved only by proposal, never past the Settle-for date without asking me, so that dates stay meaningful.
88. As a user who's ahead, I want the Coach to offer once to bring dates earlier, so that I'm not pushed but can be rewarded.
89. As a user, I want any message to the Coach ("sick this week", "work is crazy this month") to be able to trigger a Pause suggestion or a proposed Time budget cut, so that the Plan follows my life.
90. As a user, I want every response about a miss to be warm, one line of acknowledgement and one next step, with no guilt, lessons or streaks, so that I keep coming back.

### Pause

91. As a user, I want to Pause one Aspiration or all of them (rest of today, a few days, until I resume), from the app or chat, starting immediately, so that I can step back when life happens.
92. As a user, I want Actions inside a Pause set aside, counting neither as done nor missed, so that a Pause never costs me.
93. As a user coming back from a Pause, I want one "welcome back" asking whether to Catch up or shift dates, and an easier first week, so that I return gently.
94. As a user who's been silent 14 days, I want the Coach to Pause everything and send a single "I'm here when you're ready", so that I never return to a pile of missed Actions.

### Progress, Pace, Projection and Measure

95. As a user, I want Progress to open on a This week / Last week card showing hours given versus planned in total and per Aspiration, so that I see what I did.

### Guides and safety

112. As a user, I want a short Guide on Actions that need know-how (recipes with a shopping list, exercises with sets, reps and rest, what to study), fitted to my equipment, skill, likes and limits, so that I know exactly what to do.

### Operator (the developer)

## Implementation Decisions

### Architecture

- **Phone app**: React Native + Expo (TypeScript, strict), Android only for v1. Continuous Native Generation with config plugins and a development build (no Expo Go); `android/` generated, not committed. Built locally with Gradle and sideloaded; EAS Build only when iOS arrives. Expo SDK 58 at the start; upgrades deliberately, about quarterly. Flutter is ruled out; Kotlin only as an Expo module if one is ever needed.
- **Navigation**: Expo Router. **Animations**: Reanimated with Gesture Handler.
- **Styling**: Unistyles 3 (pinned, with pinned `react-native-nitro-modules`, New Architecture) with Waypoint's own typed theme tokens and thin own components. Fallback if Unistyles breaks: plain `StyleSheet` with a theme context; keep components thin so the swap is mostly imports. `babel-preset-expo` is a direct devDependency (needed for release bundles).
- **Localization**: English only, but every string goes through i18next + `expo-localization` from the first screen, and layouts use start/end, never left/right, so Arabic later is a translation.
- **Backend**: self-built ASP.NET Core API with EF Core (Pomelo) on MySQL 8, in one Docker Compose file (API + MySQL).
- **Hosting, two stages**: (1) the developer's PC, reached by the phone over Tailscale, not exposed to the internet; (2) one Hetzner Cloud VPS (CPX12-class, Germany or Helsinki) with Caddy for TLS. Move to stage 2 when someone else will use Waypoint, the PC being off makes the Coach noticeably late more than about once a week, or the developer will be away longer than the two weeks of cached Actions. Database, backups and logs stay in the EU.
- **Intelligence**: every Coach call goes phone → Waypoint's server → model provider, on Waypoint's own key. The key never reaches the phone. No on-device model, no "Sign in with ChatGPT", no MCP connector, no bring-your-own key in v1.

### Domain model

Every user-owned row carries `UserId`, enforced by an EF Core global query filter. Users are keyed on Google `sub`, never email.

- **User**: Slots, total Time budget, Contact frequency (Quiet · Gentle · Chatty), quiet hours, weekly refresh day and time, exact-alarm status as last reported by the phone.
- **Slot**: days, start, end (a single day-and-time window per Slot). Slot changes apply from the next weekly refresh.
- **Aspiration**: own words, short name (≤16 characters, Coach-proposed, editable), hue (one per Aspiration), status (active · paused · maintenance · reached/closed), share of the Time budget, Hoped-for date, Settle-for date and/or Settle-for picture, reaction to a skip (gentle check · quiet re-plan · ask why). At most 3 active.
- **Interview**: per Aspiration; transcript, status (in progress · awaiting confirmation · confirmed), and the confirmed hand-off.
- **Plan version**: per Aspiration, immutable once approved; carries rationale, reason for change, ramp level, Milestones, habits, tasks, Guides and assumptions as they stood. A new version is created by every approved change (first Plan, weekly refresh, Re-plan, Catch-up, Time budget cut). A proposed version waits for approval; at most one pending proposal per Aspiration.
- **Milestone**: date, title, "reached when" line, kind (effort · ability), state (upcoming · reached · nearly there), optional Measure.
- **Measure**: name, unit, starting value, hoped-for value; readings with date and value. At most one per Milestone.
- **Action**: a habit (belongs to the Plan; "N times a week"; on Slots or on an Anchor; minutes, or optional target duration on an Anchor) or a task (belongs to a Milestone; minutes; a date or "this week" window). Optional Guide. Optional link from a prep habit to the Anchor habit it supports.
- **Anchor**: the user's words, usual time, optional days.
- **Scheduled Action** (an occurrence in the two-week window): date, Slot or Anchor, minutes, reminder time, reminder kind (now · get-ready with lead), pre-written reminder text, reminder on/off.
- **Check-in**: per scheduled Action; state (done · partly · skipped), minutes actually spent (partly), optional reason chips and free text, tapped-at time, client ID. The non-Check-in states are derived: **unreported** (no Check-in) and **set aside** (inside a Pause).
- **Pause**: scope (one Aspiration or all), start, end (end of today, a date, or open), started by (user · Coach after silence).
- **Chat message**: role, text, optional Aspiration tag, optional card (Interview summary · Guide · proposal · referral), client ID for messages from the phone.
- **Job**: kind, target row IDs only (never free text), state, attempts, next run.

The Interview's hand-off, from the prototype runner (field names indicative), extended with the domain picture and Settle-for picture decided later:

```json
{
  "user": { "slots": [{ "label": "", "days": ["mon"], "start": "07:00", "end": "07:45" }],
            "time_budget_hours_per_week": 5, "contact_frequency": "" },
  "aspiration": {
    "aspiration": "", "short_name": "", "success_looks_like": "", "why_now": "", "starting_point": "",
    "past_attempts": [{ "what": "", "what_worked": "", "what_derailed": "" }],
    "share_hours_per_week": 3, "constraints": [],
    "domain_picture": { "routine": "", "skill": "", "limits": [], "likes": [], "dislikes": [] },
    "hoped_for_date": "YYYY-MM-DD", "settle_for_date": "YYYY-MM-DD", "settle_for_picture": "",
    "on_skip": "gentle_check | quiet_replan | ask_why", "open_questions": []
  }
}
```

The `user` block is asked only in the first Interview.

### Interview

- Warm, brief, one question per turn, reflects back before asking, forgiving about past attempts, no lecturing. Target about 10–12 Coach turns (~20 minutes), not a hard cap.
- Covers: success picture, why now, starting point, past attempts (what worked, what derailed), Slots pinned to a day-and-time window with travel counted, constraints, Hoped-for date, Settle-for as date/picture/both, reaction to a skip, a domain block of 3–4 questions (routine, skill, limits, likes and dislikes), and once about health or injuries for physical Aspirations.
- Ends with the short-name step, then the second-person picture, the still-unknowns, and rows for dates, time a week and Slots. Unknowns become open questions the Coach asks later, never blockers.
- Streams over SSE; resumable at any point (the server holds the transcript); on resume the Coach recaps and repeats its last question.
- On confirmation the server enqueues a Plan job and the summary card is posted to the Coach chat.

### Plan rules

These numbers guide the Coach prompt; server code enforces only the hard rules (marked **hard**).

- **Milestones**: about 3–6; the first 2–4 weeks after start; none after the Hoped-for date, **hard**: never past the Settle-for date. "Reached when" lines are effort or ability, never outcome.
- **Rolling window**: concrete Actions only for the next ~2 weeks; later Milestones are a date and a line until the window reaches them.
- **Ramp**: start at about 60–70% of the Aspiration's share; step up one notch (one more session or a few more minutes; Anchor habits by count) per weekly refresh while the last two weeks were **mostly done**; stop at the full share.
- **Mostly done**: a week is mostly done when at least 80% of its planned minutes were done (partly counts the minutes actually spent; set-aside Actions are excluded). See Further Notes.
- **Capacity**, **hard**: no day holds more minutes in a Slot than the Slot holds. Every active Aspiration gets at least one Action a week. When two Actions compete for a Slot, the Aspiration closest to slipping past its Settle-for line wins.
- **Anchor habits**: outside the Time budget; one per Aspiration to start, at most two, about four across all; added one at a time at a weekly refresh after the current one has held ~2 weeks.
- **Approval**: every structural change (Milestones, cadence, dates, Guides at refresh) is a proposal the user approves. The user may move a single Action directly. Approving a version the server has already replaced is rejected and the phone shows the newer one.
- **Maintenance**: after the last Milestone of an open-ended Aspiration, habits continue with no Milestones and no Projection; tracked as consistency.
- The Plan output keeps the prototype's validated shape (rationale first, assumptions named, every Action on a real Slot within its length), extended with Anchors, Measures and Milestone kind. App code validates dates, counts and Slot fit regardless of the model's structured output.

### Weekly refresh and Re-plan

- Runs as a server job at the user's chosen day and time (default Sunday 18:00). Order: (1) list unreported Actions with a one-tap "did it"; (2) measure tolerance per Aspiration; (3) compute Pace, Projection states; (4) propose next week (ramp, Catch-up, Guide changes, new Anchor habit if due) as "here's what I changed". One notification; "Looks good" accepts from the shade. Ignored for a day → applied silently with a note in the app. Doesn't count toward Contact frequency.
- **Tolerance bands** per Aspiration over the last two weeks, with done and partly both counting as done (showing up counts): **Absorb** ≥70%; **Ease back** under 70%, step down one notch; **Re-think** under 30% two weeks in a row, a short warm conversation instead of a quiet cut. Unreported counts as not done here only after the "did it" list has passed; set aside never counts.
- **Between refreshes** only a message from the user or a Pause bends the Plan.
- **Misses**: a missed habit session → offer a free Slot later that week (not two sessions of the habit on one day), else let it go silently. A missed task → next free Slot with a one-line mention; slips twice → offer to split. Three Partly in a row on one Action → offer a shorter version at the next refresh.
- **Catch-up**: only in Absorb; spread over ≤ ~3 weeks, free Slots, ≤ ~20% over the share, never beyond a day's Slots; always proposed, "just shift the dates" offered. While easing back or re-thinking, shortfall moves dates instead.
- **Dates** move only by proposal, only when a Projection says a Milestone can't be met, never past Settle-for. Past Settle-for → the honest choice (cut scope / the Settle-for picture, bigger share, later date). Ahead → offer once per Milestone to bring dates earlier.
- **Messages**: "sick this week", "on holiday till the 20th" → the Coach suggests a Pause; "work is crazy this month" → a proposed temporary Time budget cut, applied on one-tap approval. A Time budget change in Settings → the Coach proposes a Re-plan.

### Pause and silence

- A Pause covers one Aspiration or all (default all), starts immediately with no approval. "Not today" is a Pause ending at midnight (one Action or everything). Reachable from the app and chat, not from notifications.
- Inside a Pause: reminders, follow-ups and nudges are silenced; Actions are set aside.
- Return: one "welcome back" (counts toward Contact frequency) asking Catch-up or shift dates; Catch-up suggested after ≤ ~2 weeks, shift dates after longer (Catch-up still offered). First week back one notch lower; Catch-up starts in week two.
- Silence (no Check-in and no app open): 3 days → one gentle nudge; 7 days → second nudge offering a Pause; 14 days → the Coach starts a Pause of everything and sends one "I'm here when you're ready"; weekly refresh prompts stop until the user returns. This auto-Pause is the only structural change without approval.

### Pace and Projection

- **Pace** per Aspiration: minutes done ÷ minutes planned over the last 4 weeks, weighted toward recent weeks; each week scored against the Plan version in force that week (by the Check-in's tapped-at time). Partly counts actual minutes; set-aside excluded from both sides; unreported counts as not done once the "did it" list has passed. Anchor habits are out of Pace (a linked prep habit on a Slot counts).
- **Remaining work**: the Aspiration's planned weekly minutes under the current version from now to the Milestone's date (works beyond the two-week window).
- **Projected date**: remaining planned weeks ÷ Pace. Range ends from the slowest and fastest weekly Pace in the window; under ~6 weeks of history never narrower than ±1 week. Said in words, never percentages.
- **Too early**: no dated Projection for the first 2 weekly refreshes of a Plan, nor the first week back from a Pause longer than ~2 weeks.
- **States**, judged only at the weekly refresh: On track (middle ≤ date); Slipping (middle past the date at two refreshes in a row → propose a later date ≤ Settle-for); Past Settle-for (optimistic end of the final Milestone past Settle-for, one refresh is enough → the honest choice; UI pill "Your call"); Ahead (late end ≥1 week early at two refreshes in a row → offer once).
- Spoken at the weekly refresh only on a state change, plus a "where you stand" line about monthly; any time the user asks; always visible in Progress.
- Pace, Projection and tolerance are deterministic server code, not model output; the Coach is given their results to phrase.

### Milestones reached, Measures

- Effort lines: worked out from Check-ins; the Coach confirms with a one-line celebration. Ability lines: a one-off test task in the last week before the date; the user reports. The user can say "I've got it" early. At a Milestone's date the Coach asks "Did you reach it?"; a no feeds a Re-plan, never a failure.
- Not reached despite the work → "nearly there": a 1–2 week extension (added to remaining work) or a lower bar; the user picks.
- Measures are read at Plan acceptance, at each Milestone, optionally ~4-weekly at the refresh, or any time; never daily, never a day-by-day chart. Out of Pace and Projection. Moving slower than hoped → propose resetting later hoped-for values to the trend, no added work. Flat or wrong way at two Milestones in a row (or ~6 weeks) → re-think *what* the work is, suggesting a professional where it fits. A lagging Measure never raises the Settle-for choice on its own.

### Guides and safety

- A Guide is optional, attached to an Action only, plain text of a few steps (~60–180 words), opening from the Action sheet and from a reminder tap. Structure from the prototype:

```json
{ "body": "", "targets": [{ "what": "", "low": 0, "high": 0, "unit": "", "why": "" }],
  "withheld": [{ "area": "", "reason": "" }], "referral": "" }
```

- Targets are ranges from mainstream guidance with reasoning; plain structural counts may be single numbers. Safe floors: no daily calorie target below 1,500 kcal (men or unknown) / 1,200 kcal (women), no deficit over ~500 kcal/day, load ramps at most one small step per refresh.
- Red flags (pain or new injury, dizziness or chest symptoms, a condition or medication in play, pregnancy, signs of disordered eating, a diagnosis request, or any of these in the domain picture): withhold amounts, timing and load in that area; general choices stay allowed; nothing loads the injured part, warm-ups included. The referral lives only in `referral` and shows as its own card; repeated at a refresh only when something new happened. Scheduling, encouragement and the rest of the Plan carry on; the Coach offers to ease or Pause affected Actions.
- A message suggesting a crisis: the Coach drops coaching and points to real help.
- Guides change at the weekly refresh (in the proposal) or right away on a chat request; each accepted change is kept with its Plan version. A Check-in reply that doesn't match the Guide → the Coach asks, never rewrites on a guess.
- Nothing is logged or counted (no food or calorie tracking).

### Coach calls and models

- Kinds of call and models, each in server configuration: **Sonnet 5.5** for Interview, Plan, Re-plan, weekly refresh proposal, chat and Guides; **Haiku 5.5** for reminder text and Check-in replies with no note; **Sonnet 5.5** for Check-in replies with a note and silence nudges. Prompts use caching for the stable system part.
- Prompts carry the confirmed Interview summary, the current Plan, recent Check-ins and a recent chat window, never the whole history, and never the user's name or email. No Batch or Files API.
- **Chat and Interview** stream over Waypoint's own SSE contract (`delta` / `done` / `error`), read with `expo/fetch` in a small hook; no Vercel AI SDK.
- **Plan, Re-plan and weekly refresh** run as server jobs; FCM "Plan ready" tells the phone.
- **Reminder text** is written in batches when Actions are planned or refreshed and stored with each scheduled Action, so reminders need no model call.
- **No model call possible** (offline, server down, provider down, spend limit hit): the Coach is late, never faked. Reminders fire locally; the outbox queues Check-ins and messages; the app shows "The Coach will reply when you're back online" / "Saved · your Coach will reply when it can"; Re-plans wait and the current Plan stays in force. Jobs retry with backoff.
- **Spend guard**: $10/month hard limit in the provider console, alert at $8. No in-app metering in v1.

### Server jobs and push

- A jobs table in MySQL polled by an in-process `BackgroundService`, with retries and backoff; no Hangfire or Quartz. Job kinds: Plan generation, Re-plan, weekly refresh (including the two-week Action window and reminder text), unprompted Coach messages within Contact frequency, silence nudges, auto-Pause after 14 silent days, auto-apply of an ignored weekly proposal.
- FCM HTTP v1 via `FirebaseAdmin` (C#), only for Coach messages, silence nudges, "Plan ready" and the weekly refresh prompt. High-priority messages always show a notification.
- **Contact frequency** caps unprompted messages across all Aspirations: Quiet (a few times a week), Gentle (up to once a day), Chatty (up to three a day). Replies to the user's own messages never count; reminders never count; the weekly refresh prompt doesn't count; silence nudges and "welcome back" count (nudges ignore Quiet's spacing). Over the cap, the message for the Aspiration closest to its Settle-for line wins. Messages landing in quiet hours (default 21:30–07:00) are held until they end and dropped if stale.

### Reminders on the phone

- Local alarms via `expo-notifications`, not FCM or WorkManager. Exact (`setExactAndAllowWhileIdle`) when "Alarms & reminders" (`SCHEDULE_EXACT_ALARM`) is granted, else inexact (`setAndAllowWhileIdle`). `USE_EXACT_ALARM` is not used. Inexact window is 75% of the lead time capped at 1 h, plus up to ~15 min of Doze, so each reminder is armed close to its time: one alarm per upcoming reminder, re-armed as each fires, and re-armed on `BOOT_COMPLETED` and app start.
- One reminder per Action: "now" at the Slot start (or Anchor's usual time); "get-ready" once at a lead time (default ~1 h or the morning of the day), set by the Coach, editable per Action. Never a second ping at the start.
- Reminders due at the same moment (Anchor reminders within ~30 min) share one grouped notification, a child per Action, each with **Done · Partly · Skip**; Partly is an inline reply for minutes.
- Tapping a button runs a headless Expo `TaskManager` task with the app killed (verified on Android 16); the task parses the data from `request.content.dataString` (not `content.data`), writes the Check-in to the outbox, clears the notification and attempts a send.
- Follow-up: at most one, at Slot end, same buttons; not sent if the user interacted that day, a Pause is on, it's a habit that can still happen this week, or the last two Actions went unreported. Anchor Actions get none; their reminder stays in the shade.
- After ~3 weeks at or near target, the Coach offers once to stop an Anchor habit's reminder; it returns if the habit slips at a refresh. The user can switch any habit's reminder off.
- Reminders fire inside quiet hours if the user's Slot is there; they don't count toward Contact frequency.
- Permissions: notifications, then exact alarms, one at a time right after the first Plan is approved. If exact alarms are declined, ask again only if Check-ins show reminders landing badly.
- OEM battery killers: if silence nudges or Check-in timing show reminders aren't landing, deep-link to the device's battery setting.

### Phone storage and sync

- The server is the source of truth. The phone caches the next two weeks of scheduled Actions with reminder text and Guides, the current Milestones, latest Projections and recent chat, in expo-sqlite behind a small storage interface (so a web client can swap stores). The phone never changes a Plan itself.
- **Outbox**: Check-ins, messages to the Coach, Pauses, Plan approvals and single-Action moves each get a client ID and are sent in order on reconnect; the server treats client IDs idempotently. A Check-in carries its tapped-at time. A Check-in changed twice keeps the latest tap.
- After the outbox drains, the phone pulls changes since its sync cursor.
- Refresh tokens in Android Keystore via secure storage; no extra database encryption (Android file-based encryption and app sandbox). Sign-out wipes the cache, outbox and tokens.

### Auth

- Google only. Android Credential Manager gets a Google ID token; the API verifies it and issues its own short-lived access token (~15 min) and a rotating refresh token stored hashed.

### Data, privacy and operations

- **Retention**: no automatic expiry; everything under an Aspiration lives until it's deleted.
- **Export**: one action producing a zip with complete JSON and readable Markdown.
- **Delete**: one Aspiration or the whole account, hard-deleted from the live database at once; nightly dumps kept 30 days roll it off; no single-user restores from backup. The app says so plainly.
- **Encryption**: encrypted disk and encrypted off-machine nightly dumps; no field-level encryption in v1 (revisit with a second user).
- **Logs**: IDs, timings, token counts and error types only; free text never in logs, error traces or job payloads.
- **Model provider**: standard API retention accepted (not used for training, deleted within 30 days, up to 2 years if flagged by safety systems, processed outside the EU). The app's privacy note says so. Zero retention or an EU route is server config for when a second user arrives.
- **Ops**: one restore drill before real data. Stage 2 adds unattended security upgrades, SSH by key only, a firewall open only on 443 and SSH, and a free external uptime check.

## Testing Decisions

- **What makes a good test**: it drives the system through a public seam and asserts what a user or the phone would observe (responses, stored state read back through the API, notifications queued), never private methods or EF internals. Time is injected, so weekly refreshes, silence thresholds and Pauses are tested by advancing a fake clock, not by waiting.
- **Seam 1 (main): the server's HTTP API**, in-process (ASP.NET `WebApplicationFactory`) against real MySQL in Testcontainers, with a fake model client (scripted replies, including structured Plan JSON and failures) and a fake FCM sender. Jobs run by stepping the job runner in the test. This one seam covers sign-in and token rotation, `UserId` isolation, Interview → Plan → approval, the outbox's idempotent sync and stale-approval rejection, weekly refresh (unreported list, tolerance bands, ramp, Catch-up), Pace and Projection states, Pause and silence (3/7/14 days), Contact frequency and quiet hours, the Coach-late path, export and delete.
- **Seam 2: the phone's storage interface and Check-in task**, with Jest: the outbox ordering and client IDs, applying synced changes from a cursor, parsing `content.dataString` in the headless task, and reminder arming rules (one per Action, grouping, follow-up conditions, re-arm). Screens get no unit tests in v1; they're verified on the device against the prototype.
- **Seam 3: Coach prompt evals**, not part of the build: the prototype runners (Interview, Plan with its automatic Slot-fit check, Guides with the red-flag case, blind model eval) are the prior art for re-running prompts against fixed hand-offs and personas whenever a prompt or model changes.
- **Device checks** before calling v1 done: killed-app Check-in from shade and lock screen, exact and inexact reminder timing, re-arm after reboot, Force stop and Samsung "Deep sleeping apps" (untested so far).
- No existing test code: Waypoint is greenfield.

## Out of Scope

- **Public release work**: Play Store listing, billing, onboarding for strangers, marketing. Foundations shouldn't block it later.
- **iOS, web and macOS clients**: Android only; Expo keeps iOS and web in one codebase. iOS killed-app Check-ins need their own spike; web gets no local reminders.
- **Arabic and other languages**: English only; strings and start/end layouts are ready for Arabic.
- **Integrations**: Health Connect, calendar, Google Tasks. Actions are self-reported. Calendar-aware scheduling is the first v2 candidate.
- **Other intelligence routes**: on-device models, "Sign in with ChatGPT", an MCP connector / ChatGPT App companion, bring-your-own key. The MCP connector is a v2 candidate.
- **Food logging and calorie counting**, nutrition databases. Coach-written Guides are in scope.
- **Field-level encryption**, zero-retention or EU-hosted model route, in-app spend metering: revisit with a second user.
